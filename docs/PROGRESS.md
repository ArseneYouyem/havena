Les caractères accentués français (é, à...) restent inchangés, ils sont bien supportés par la police de base.

Aucun bug détecté après génération.
- 2026-09-29 — Phase 11 : **Modèles de documents** (cahier des charges §17). Plutôt que d'ajouter un bouton « Générer PDF » dispersé dans chacun des 7 modules existants (Clients, Logements, Interventions, Prestataires, Abonnements, Finances, Inspections), création d'un module `Documents` unique et autonome : un sélecteur de type de document, un sélecteur de l'élément concerné (filtré selon le type), puis génération + aperçu PDF. Ce module ne crée aucun repository : il réutilise ceux déjà enregistrés par les bindings des autres modules (doit donc être déclaré après eux dans `AppPages`), ce qui évite toute duplication d'accès aux données. 9 générateurs PDF suivant le pattern de `RapportPdfGenerator` (même charte, même piège Unicode Helvetica déjà documenté) + un 10e générateur statique pour la procédure interne du coordinateur (15 étapes du cahier des charges §15, aucune entité liée). Devis et Facture sont rattachés à une Intervention (montants déjà présents sur cette entité) ; le Reçu de paiement est rattaché à une transaction Finances ; le Contrat d'abonnement à un Abonnement. Bug détecté et corrigé via `flutter analyze` (pas par les tests) : une police de caractères en italique (`fontStyle: pw.FontStyle.italic`) combinée à `const pw.TextStyle(...)` provoquait une erreur d'évaluation de constante à la compilation (le constructeur `TextStyle` du package `pdf` calcule certains champs dans sa liste d'initialisation à partir de `fontStyle`/`fontWeight`, ce qui n'est pas compatible avec `const` dans ce cas précis) — corrigé en retirant simplement le mot-clé `const` sur ce style précis. La table `ModelesDocuments` (créée en Phase 1, prévue pour des modèles de texte éditables par la Fondatrice avec placeholders) n'est pas utilisée : les documents sont générés par du code Dart fixe, plus simple et suffisant pour une première version fonctionnelle (cahier des charges §20 : ne pas complexifier inutilement). Validé par un test d'intégration dédié couvrant les 10 documents (signature `%PDF-` vérifiée pour chacun) en plus du build macOS.

Aucun bug détecté après génération (écrit directement, sans délégation, vu le nombre de branches à garder cohérentes entre elles). Validé par un test d'intégration dédié (recherche, éléments liés, détails) en plus du build macOS.
