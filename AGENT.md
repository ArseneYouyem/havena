## Contexte projet

HAVENA est un logiciel de gestion pour un service de type HomeCare / Inspection & Property Care (clients, logements, abonnements, inspections, interventions, prestataires, finances, rapports). Il doit fonctionner sur Windows, macOS, iOS et Android, en priorité **hors connexion** (offline-first), avec une synchronisation explicite vers Google Drive.

Le développement se fait **desktop d'abord** (Windows/macOS). L'UI desktop est dense, multi-panneaux, avec sidebar. L'UI mobile viendra ensuite et peut être différente (plus simple, linéaire) — le responsive n'impose pas un design identique entre plateformes.

## Stack technique imposée

- Flutter SDK `^3.10.8`
- State management + navigation : **GetX** (`get`)
- Stockage local léger (préférences, cache, objets simples) : **GetStorage**
- Base de données locale principale (métier, relationnelle) : **Drift (SQLite)** — `drift`, `drift_flutter`, `path_provider` (deps), `drift_dev` + `build_runner` (dev deps). Depuis Drift 2.32+/sqlite3 3.x, SQLite est bundlé automatiquement sur toutes les plateformes natives (via native assets) : ne pas ajouter `sqlite3_flutter_libs`, il est obsolète (marqué `+eol`) et inutile.
- Synchronisation distante : Google Drive, Google Sheets et Google Calendar via les **API Google Cloud Platform** (projet Firebase `havena-9edff`), en opération explicite (pas de sync automatique silencieuse imposée)
- Authentification et gestion des rôles : **Firebase Auth** (email/mot de passe) + **Cloud Firestore** (liaison compte↔rôle uniquement — voir section « Authentification et rôles »)

## Règles d'architecture impératives

- Structure **feature-first** sous `lib/` : `app/`, `core/`, `features/<feature>/`, `shared/`.
- Séparation stricte **vue / controller**. Aucune logique métier dans les vues.
- Les vues sont des `GetView<XController>` et n'appellent que des méthodes du controller.
- Les controllers ne touchent jamais directement la base de données, Firestore ou l'API Drive : ils passent par des `services`/`repositories`.
- Navigation **centralisée** via `app/routes/` (`AppRoutes`, `AppPages`). Sur desktop, un seul `AppShellView` (route unique, montée une fois) héberge en permanence `DesktopShell` (sidebar + topbar fixes) ; le changement d'onglet ne fait PAS un `Get.toNamed` (qui rejouerait toute la page avec une transition) mais met à jour `NavigationController.currentRoute` (Rx), écouté par un `Obx` qui ne change que le contenu central. Ne jamais recréer le shell à chaque navigation. `AppRoutes` reste la source de vérité des identifiants de section même si toutes ne sont pas des `GetPage` séparées.
- Composants UI réutilisables dans `shared/widgets/` (pas de duplication de composants entre features).
- Chaque entité métier possède une référence unique au format `HAV-XXX-000001` (voir cahier des charges), générée par `ReferenceGeneratorService` (`core/references/`) — jamais saisie manuellement dans un formulaire.
- La gestion des conflits de synchronisation doit être prévue dès la conception des modèles (champs `updated_at`, `updated_by`, statut de sync).
- Couleurs : utiliser exclusivement la charte définie dans `AppColors` (voir section « Charte graphique »), jamais de couleur en dur dans une vue.

## Conventions de nommage

- Fichiers : `snake_case.dart`
- Controller : `XxxController` — Binding : `XxxBinding` — View : `XxxView`
- Repository : `XxxRepository` — Service : `XxxService` — DAO : `XxxDao`

## Choix base de données locale

**Drift (SQLite)** a été retenu parmi 3 options (Drift, Isar, sqflite/sqlite3 direct).

Justification : HAVENA est un système fortement relationnel (clients → logements → abonnements → inspections → interventions → prestataires → finances), avec des besoins d'agrégation (tableau de bord, rapports mensuels, CA/marges) qui demandent des jointures SQL. Drift apporte en plus des requêtes réactives (`Stream`) qui s'intègrent naturellement avec les `Rx`/`Obx` de GetX, des migrations gérées et un typage strict. Le schéma vit dans `core/database/` (tables, DAOs, migrations), jamais accédé directement par les controllers — toujours via `repositories`.

## Export PDF

`lib/core/pdf/rapport_pdf_generator.dart` est le pattern de référence pour tout document PDF, avec `package:pdf` (widgets `pw.*`) + `package:printing` (`Printing.layoutPdf` pour l'aperçu/impression natif). **Piège connu** : la police de base (Helvetica) ne supporte QUE le Latin-1/WinAnsi — les caractères accentués français (é, à, ç...) s'affichent normalement, mais des symboles comme le tiret cadratin « — », « ✓ », « ✗ » ne s'affichent PAS (glyphe manquant, silencieux à l'analyse statique). Toujours tester la génération réelle (vérifier les logs `flutter test` pour "Unable to find a font to draw..."), pas seulement vérifier que les octets produits commencent par `%PDF-`. Préférer un tiret simple `-` et des libellés texte (`[Oui]`/`[Non]`) aux symboles Unicode. **Autre piège** : ne jamais combiner `fontStyle: pw.FontStyle.italic` avec un `const pw.TextStyle(...)` — le constructeur `TextStyle` du package `pdf` calcule certains champs dans sa liste d'initialisation à partir de `fontStyle`/`fontWeight`, ce qui casse l'évaluation de constante à la compilation (`const_eval_type_bool_num_string`) ; retirer simplement `const` sur ce style précis.

Les 9 autres générateurs de `core/pdf/` (fiche client/logement/intervention/prestataire, devis, facture, reçu de paiement, contrat d'abonnement, checklist d'inspection — cahier des charges §17 « Modèles de documents ») suivent exactement ce même pattern et sont pilotés par `lib/features/documents/` (voir section suivante). `ProcedureCoordinateurPdfGenerator` est un cas particulier : contenu 100% statique (15 étapes du cahier des charges §15), aucune entité liée, aucun paramètre.

## Authentification et rôles

**Implémenté** (`lib/features/auth/`, `lib/features/access_management/`, `lib/core/auth/role_permissions.dart`).

- Rôles fixes définis par le cahier des charges : `AppRole.fondatrice` (accès complet), `AppRole.coordinateur`, `AppRole.agent` (uniquement inspections). La matrice rôle→routes est codée en dur dans `RolePermissions` (jamais éditable à distance).
- Firestore (collection `users`, doc id = uid Firebase Auth) ne stocke que la liaison compte↔rôle : `email` (string), `fullName` (string), `role` (string, une des valeurs de `AppRole` : `fondatrice`/`coordinateur`/`agent`), `active` (bool), `createdAt` (timestamp), `createdBy` (string, uid du créateur) — jamais les permissions elles-mêmes. Règles de sécurité dans [firestore.rules](firestore.rules) : `users` (lecture de son propre doc ou, pour la Fondatrice, de tous ; écriture réservée à la Fondatrice) + les 9 collections de synchronisation des données métier (`clients`, `logements`, `abonnements`, `interventions`, `prestataires`, `finances`, `rapports`, `inspections`, `calendrier_evenements` — lecture/écriture pour tout compte actif, suppression de document toujours bloquée puisque le modèle est en suppression douce). Toute autre collection reste fermée par défaut. À déployer avec `firebase deploy --only firestore:rules` (pas fait automatiquement, nécessite `firebase login`) — **sans ce déploiement, la synchronisation Firestore des données métier échouera en pratique** (règles par défaut = accès refusé).
- Seule la Fondatrice voit l'onglet « Gestion des accès » (`AccessManagementContent`) : rôles/permissions en lecture seule + liste des comptes + formulaire d'ajout d'administrateur. La création de compte passe par une instance Firebase secondaire (`FirebaseAuthService.createUserWithSecondaryApp`) pour ne jamais déconnecter la session de la Fondatrice.
- `AuthRepository.login()` (Firebase Auth + fetch Firestore ponctuel) met le résultat en cache local via `AuthSessionCacheService` (GetStorage, clé `auth_session`). Au démarrage, `AuthRepository.tryResumeSession()` relit ce cache **sans appel réseau** (résolu de façon synchrone dans `main()`, avant même `GetMaterialApp`, pour choisir la route de départ : `AppRoutes.login` ou `AppRoutes.dashboard`). Le rôle n'est jamais re-fetché automatiquement : uniquement via `AuthRepository.refreshSessionFromRemote()`, à appeler lors d'une synchronisation explicite. Toujours utiliser des lectures Firestore ponctuelles (`.get()`), jamais `.snapshots()`.
- Filtrage : `SidebarMenu` n'affiche que les sections accessibles au rôle courant (`SessionController.canAccess`) ; `AppShellView` a un garde-fou qui redirige vers la première route autorisée si `NavigationController.currentRoute` pointe vers une section non permise.

## Modules métier — pattern de référence

`lib/features/clients/` et `lib/features/logements/` sont le pattern canonique (CRUD simple) à reproduire pour chaque futur module métier : `repository` (seul point d'accès au DAO Drift + au `ReferenceGeneratorService`), `controller` (état de liste via `StreamSubscription` sur `repository.watchAll()`, état de formulaire en champs `Rx`/`Rxn` séparés, `openCreateForm()`/`openEditForm()`/`submitForm()`), `binding` (enregistre repository puis controller en `lazyPut`), `view` exportant un widget `XxxContent` SANS `DesktopShell` (liste + recherche live + dialog de formulaire, à la manière de `access_management_view.dart`). Les vues `XxxContent` sont branchées dans `AppShellView._buildContent()` selon la route, jamais dans une `GetPage` séparée. Un module qui référence un autre (ex. Logements → Clients pour le dropdown) injecte le repository de l'autre feature dans son controller.

Pour un module trop riche pour un simple dialog (ex. `lib/features/inspections/` : checklist + photos + validation), le même `XxxContent` bascule en interne entre une vue LISTE et une vue DÉTAIL selon un état du controller (`Rxn<int> selectedXxxId`, avec une méthode `selectXxx(int? id)` qui gère l'abonnement `Stream` dépendant de la sélection) — jamais via une nouvelle `AppRoutes`/`GetPage`. Un bouton retour dans la vue détail remet la sélection à `null`.

**Briques partagées pour les photos** : `lib/features/photos/repositories/photos_repository.dart` (singleton permanent, `Get.find<PhotosRepository>()` disponible partout) + `lib/core/storage/file_storage_service.dart` (copie un fichier importé vers le stockage applicatif, classé par logement : `HAVENA/photos/<référence logement>/<dossier catégorie>/<référence logement>_<référence entité>_<TYPE>_<NN>.<ext>`, cahier des charges §16 — 5 dossiers numérotés selon `PhotoType`, voir `lib/core/storage/photo_category.dart` : `photoCategoryFolder()`, réutilisée à l'identique par le stockage local ET par la synchronisation Drive pour garder les deux arborescences cohérentes). `FileStorageService` prend un `Directory? baseDirectory` optionnel pour être testable avec un vrai répertoire temporaire (même principe que `AppDatabase([QueryExecutor? executor])`), car `path_provider` ne fonctionne pas dans `flutter test`. Tout appelant de `PhotosRepository.addPhotoFromFile` doit résoudre et passer la référence du LOGEMENT (pas seulement celle de l'entité liée), même pattern que `_findLogement()` dans `InspectionsController`/`InterventionsController`. Import de fichiers via `file_picker` (déjà installé) : API du package en v13+, `FilePicker.pickFiles(type: FileType.image)` est **statique** (pas de `.platform`) et retourne directement `Future<List<PlatformFile>>` (jamais null, pas de paramètre `allowMultiple` — `pickFiles` est toujours multiple, `pickFile` singulier existe séparément). Vérifier la doc de la version installée avant de régénérer du code l'utilisant, l'API a changé entre versions majeures.

**Cas particulier — module transversal sans état propre** : `lib/features/documents/` (§17 « Modèles de documents ») ne suit PAS le pattern CRUD ci-dessus car il ne possède aucune donnée propre : sa `DocumentsBinding` ne crée aucun repository, elle réutilise via `Get.find()` ceux déjà enregistrés par les bindings des 7 autres modules métier — elle doit donc être déclarée APRÈS eux dans la liste `bindings` d'`AppPages`. Son controller choisit le repository/générateur PDF adapté selon un type sélectionné (`DocumentKind`, enum propre à la vue, sans lien avec la table Drift `ModelesDocuments`). La table `ModelesDocuments`/`ModelesDocumentsDao` (créée en Phase 1, colonne `contentTemplate` prévue pour des modèles de texte éditables par la Fondatrice avec placeholders) existe en base mais n'est reliée à aucune UI : amélioration future volontairement différée, les documents actuels sont générés par du code Dart fixe (plus simple, conforme au cahier des charges §20 qui déconseille de complexifier avant d'avoir testé une première version).

**Cas particulier — contrôleur au niveau du shell** : `ReferenceSearchController` (`lib/app/controllers/`, cahier des charges §9 « recherche transversale ») suit le même principe « sans repository propre » que Documents, mais vit dans `app/` (pas `features/`) et sa vue (`ReferenceSearchField`, `shared/widgets/layout/`) est montée dans la topbar (`DesktopShell`) plutôt que routée via `AppShellView._buildContent()` : elle doit rester accessible depuis n'importe quelle section active, pas seulement un onglet dédié. `ReferenceSearchBinding` est déclarée en dernier dans `AppPages` (après tous les repositories qu'elle réutilise).

## Synchronisation Google Drive / Firestore

**Identifiants** : `google_drive_credentials.json` (identifiant OAuth « Desktop app » exporté depuis la console Google Cloud du projet `havena-9edff`) ne doit **jamais** être commité — il est dans `.gitignore`, `google_drive_credentials.example.json` documente le format attendu pour quiconque configure le projet. Il est déclaré comme asset Flutter (`pubspec.yaml`) pour être embarqué dans le binaire packagé, pas seulement disponible en dev.

**Architecture** (`lib/core/sync/`) : `GoogleDriveCredentialsLoader` (charge l'identifiant depuis l'asset) + `GoogleDriveTokenCache` (persiste uniquement le refresh token via `GetStorage`, jamais l'access token qui expire vite) + `GoogleDriveAuthService` (flux OAuth « installed application » — `googleapis_auth`'s `clientViaUserConsent` ouvre le navigateur système et écoute une redirection locale ; `clientViaRefreshToken` reconstruit un client authentifié sans navigateur au démarrage suivant) + `GoogleDriveSyncService` (utilitaire Drive générique : `ensureFolderPath`/`uploadFile`, ne connaît rien du schéma métier HAVENA — la correspondance « quelle entité va dans quel dossier » reste dans l'appelant, ex. `SyncController` pour les photos). `SyncController` (`lib/app/controllers/`) suit le même principe « sans repository propre » que `DocumentsController`/`ReferenceSearchController` — `SyncBinding` déclarée en dernier dans `AppPages`. Statut visible et actions explicites (connexion / sync manuelle / déconnexion) via `SyncStatusIndicator` dans la topbar (cahier des charges : « bouton explicite, statuts de sync »).

**Limite de test connue** : le flux OAuth réel (clic de consentement dans un navigateur) et l'upload Drive ne peuvent pas s'exécuter dans `flutter test` — ni `GoogleDriveTokenCache`, qui dépend de `GetStorage`, lequel appelle `path_provider` de façon **inconditionnelle** même quand un chemin explicite est fourni (`MissingPluginException` en environnement de test, même limitation que Firebase). Seule la logique pure est testée unitairement (`parseCredentials`, `driveContentTypeFor`, `escapeDriveQueryValue` — fonctions top-level extraites exprès des classes de service pour rester testables sans réseau ni plugin). Toujours vérifier le reste via un vrai lancement de l'app.

**Identité de synchronisation (`syncId`)** : les `id` locaux auto-incrémentés et les références `HAV-XXX-000001` sont générés **indépendamment par chaque appareil** et peuvent donc entrer en collision entre appareils créés hors-ligne (deux appareils peuvent attribuer le même `HAV-CLI-000005` à deux clients différents). Chaque table métier référençable (Clients, Logements, Abonnements, Interventions, Prestataires, Finances, Rapports, Inspections, Calendrier) porte donc une colonne `syncId` (UUID, générée à la création dans chaque `repository.create()` via `const Uuid().v4()`, jamais affichée à l'utilisateur) — schéma v2, migration dans `AppDatabase.migration` avec backfill des lignes existantes. **Règle impérative** : `syncId` est la SEULE clé utilisée pour la synchronisation Firestore ; `id` reste purement local (jamais comparé entre appareils) et `reference` reste purement un identifiant d'affichage/impression, généré immédiatement à la création (offline-first) et donc jamais garanti unique entre appareils avant une éventuelle synchro (collision cosmétique acceptée, sans impact sur l'intégrité des données puisque tout est relié par `syncId`).

**Clés étrangères : pas de retype en UUID.** `logementId`, `clientId`, `prestataireId`, etc. restent des entiers locaux inchangés dans le schéma et dans tout le code existant (repositories, controllers, dropdowns) — décision explicite avec l'utilisateur pour ne pas réécrire les modules déjà construits et testés. La traduction id local ↔ `syncId` (nécessaire parce qu'un `id` local ne veut rien dire sur un autre appareil) se fait **uniquement à la frontière du moteur de synchronisation** : au push, l'adaptateur de l'entité remplace l'`id` local par le `syncId` du parent avant d'écrire le document Firestore ; au pull, il fait l'inverse (retrouve/crée le parent local via son `syncId`, puis utilise son `id` local pour la relation).

**Répartition des données synchronisées** (décidée avec l'utilisateur, cahier des charges §2/§7/§9) :
- **Fichiers** (photos, PDF générés) → Google Drive, arborescence identique au stockage local (voir `photoCategoryFolder`).
- **Vue tableur** (Google Sheet, un onglet par module) → générée depuis la BD locale, **lecture seule**, jamais réinjectée dans l'app. Explicitement pour éviter de retomber dans l'écueil que le cahier des charges dénonce lui-même (§9 : « je ne veux pas seulement des fichiers Google Sheets, je veux un système où les informations sont liées entre elles »). Implémenté par `GoogleSheetsExportService` (`core/sync/`) : réutilise directement les `EntitySyncAdapter` déjà branchés sur Firestore (`allLocal()`/`toFirestoreMap()`) — un classeur unique « HAVENA » (retrouvé ou créé dans Drive), un onglet par `collectionName`, effacé puis réécrit en entier à chaque synchronisation. `businessSheetHeaders`/`businessSheetTabTitles` (constantes) fixent les colonnes affichées par module — ajouter une colonne à un export existant ne touche que cette constante. Limite assumée : les clés étrangères s'affichent en UUID technique (`clientSyncId`...), pas en nom résolu — vue de convenance, pas une relation, pour rester simple (cahier des charges §20).
- **Données métier** (Clients, Logements, Interventions...) → Firestore (déjà utilisé pour l'auth/rôles), SQLite restant la copie locale hors-ligne. Chaque appareil a sa propre base SQLite isolée : sans cette extension Firestore, rien ne fait circuler les données entre appareils (Drive stocke des fichiers, pas des données relationnelles).

**Stratégie de conflit** (décidée avec l'utilisateur) : pull (récupère les enregistrements Firestore modifiés) → merge local → push. Écrasement automatique et silencieux **uniquement** quand un seul côté a changé depuis la dernière synchro connue (comportement normal d'un pull, pas un risque). Vrai conflit (les deux côtés ont changé) → fenêtre de résolution **générique** (indépendante du type d'entité, une liste de champs en désaccord) avec 3 actions globales (Tout garder local / Tout garder cloud / Fusion automatique — priorité à la valeur remplie, puis au local en cas de double changement sur le même champ) et un choix individuel Local/Cloud par champ, modifiable même après un choix global.

**Moteur de synchronisation (`core/sync/`) — pattern à répliquer par module** : `SyncClassifier` (pur, décide pushLocal/pullRemote/conflict/noChange en comparant `updatedAt` local/distant à la dernière synchro connue de l'appareil) et `FieldMergeResolver` (pur, diff champ par champ + fusion auto + application de choix explicites) ne dépendent d'aucun réseau — entièrement testés en `flutter test`. `SyncGateway` est le contrat d'accès à une collection distante générique (`Map<String, dynamic>`, dates toujours en ISO 8601 — jamais de `Timestamp` Firestore dans cette couche) ; `FirestoreSyncGateway` l'implémente réellement (nécessite `Firebase.initializeApp()`, donc non testable en `flutter test` — même limite que Firebase Auth/Google Drive), `InMemorySyncGateway` est une implémentation réelle en mémoire (pas un mock) utilisée pour tester `SyncEngine` de bout en bout avec une vraie base Drift. `SyncEngine.syncEntity<T>(EntitySyncAdapter<T> adapter, {lastDeviceSyncAt})` orchestre pull/merge/push pour un type d'entité et retourne la liste des `SyncConflict` détectés (rien n'est écrasé pour eux).

Pour ajouter un nouveau module métier SANS clé étrangère (suivre `features/clients/sync/client_sync_adapter.dart` comme référence — Clients, Prestataires, Calendrier) :
1. Implémenter `EntitySyncAdapter<T>` dans `features/<module>/sync/<module>_sync_adapter.dart` : `collectionName`, `syncIdOf`, `updatedAtOf`, `allLocal()` (= `repository.watchAll().first`), `toFirestoreMap` (sérialise tous les champs, dates en ISO 8601), `upsertLocal` (délègue à `repository.upsertFromRemote({syncId, data})`).
2. Ajouter au repository : `findBySyncId(String)` (filtre en mémoire sur `watchAll().first`) et `upsertFromRemote` (crée ou met à jour selon que `findBySyncId` trouve une ligne existante ; `syncStatus: SyncStatus.synced` sur le résultat, jamais `.local`).
3. Enregistrer l'adapter dans `SyncBinding` et l'ajouter à `businessAdapters`.

Pour un module AVEC clé étrangère vers un parent déjà synchronisé (suivre `features/logements/sync/logement_sync_adapter.dart` — `clientId` nullable — et `features/rapports/sync/rapport_sync_adapter.dart` — `logementId` obligatoire) :
1. Le repository de l'entité reçoit en plus le repository du PARENT dans son constructeur (ex. `LogementsRepository(dao, referenceGenerator, clientsRepository)`) — **répercuter ce changement de signature dans le binding du module ET dans tous les fichiers de test qui instancient ce repository directement** (`flutter analyze` les repère tous, aucun oubli possible).
2. `toFirestoreMap` (dans l'ADAPTATEUR, pas le repository, pour rester synchrone) : remplace `xxxId` (entier local) par `xxxSyncId` (UUID du parent, **nom de clé différent** pour ne jamais confondre avec un entier) — pas de clé `xxxId` du tout dans le document Firestore. Pour retrouver le parent sans await, l'adaptateur charge sa liste complète dans un champ privé à chaque appel d'`allLocal()` (ex. `_cachedClients = await _clientsRepository.watchAll().first;`) et fait le lookup en mémoire.
3. `upsertFromRemote` (dans le repository) : lit `data['xxxSyncId']`, retrouve le parent local via `parentRepository.findBySyncId(...)`. Si la clé étrangère est **nullable** et le parent introuvable localement (pas encore synchronisé sur cet appareil) : mettre `null`, ne pas bloquer. Si elle est **obligatoire** (ex. `Rapports.logementId`) et le parent introuvable : `return;` immédiatement, sans rien insérer ni mettre à jour — l'enregistrement sera retenté à la prochaine synchronisation, une fois le parent arrivé.
4. Dans `SyncBinding`, déclarer `businessAdapters` dans l'ordre **parent avant enfant** (ex. Clients puis Logements puis Rapports) : sur un nouvel appareil, le premier pull doit trouver le parent déjà en local pour que la traduction fonctionne dès le premier passage.

`SyncConflictDialog` (`shared/widgets/layout/`) reste inchangée pour toute nouvelle entité, avec ou sans clé étrangère : elle ne travaille que sur des `Map<String, dynamic>` génériques.
